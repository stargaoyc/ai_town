# 0003 - 多模型源按序切换 + 失败冷却

- 状态：Accepted
- 日期：2026-08-23
- 关联：roadmap #23、docs/archive/gap-analysis.md §7.1.13（yuiju 对标）

## 背景（Context）

LLM 调用原为单一 endpoint（`settings.openai_*`）。供应商故障/限流时只有两条路：
请求失败重试后抛错（Tick 整轮跳过），或熔断器打开（全部调用短路）。
对陪伴类产品，角色「集体失联」的体验伤害远大于换一个略差的模型继续对话。

熔断器解决的是「快速失败」，不解决「换条路继续成功」。

## 决策（Decision）

**在 LLMClient 内置多源池：主源 + `LLM_FALLBACK_SOURCES` 备用源（JSON 数组，
每项 `{api_key, base_url, model?}`）。调用时按序尝试；某源失败进入 5 分钟冷却，
候选顺序变为「未冷却按配置顺序在前，冷却中排末尾仍可兜底」；全部失败抛最后
一个异常，交由上层统一挂载的预算检查与熔断器处理。**

- 冷却语义是进程内的（`time.monotonic()`），不做分布式共享——单实例部署下
  每实例独立探测即可，避免为冷却状态再引入 Redis 往返。
- 备用源允许配置不同 `model` 名（OpenAI-compatible 网关间模型名可能不同）。

## 备选方案（Alternatives）

| 方案 | 否决原因 |
|------|----------|
| LangChain `with_fallbacks` | 无法表达「冷却中降级到末尾而非直接剔除」；异常类型路由配置繁琐 |
| 冷却状态存 Redis（跨实例共享） | 单实例场景引入每次调用的额外往返；多实例误报会互相传染冷却 |
| DNS/网关层故障转移 | 需要基础设施改动；且无法处理「同网关不同配额」的场景 |

## 后果（Consequences）

**正面**

- 主源抖动时自动降级到备用源，恢复后（冷却过期）自动切回。
- 与熔断器正交：fallback 解决「换路」，circuit breaker 解决「止损」。

**负面 / 义务**

- 各源模型能力不同时，输出质量在切换窗口内波动——文档要求备用源尽量同型号。
- 冷却是进程态：进程重启即清零，重启风暴场景下会对故障主源重新探测（可接受，
  探测成本低）。
